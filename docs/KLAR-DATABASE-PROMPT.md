# Готовый промпт: PostgreSQL + Prisma для Klar

Ты — senior backend-разработчик и архитектор PostgreSQL. Спроектируй и реализуй серверное хранение данных существующего приложения Klar, сохранив весь локальный прогресс и подготовив основу для рейтингов и онлайн-соревнований.

## Контекст и границы

Проект: React + TypeScript + Vite + Tailwind v4, PWA, RU/UK. Сейчас данные пользователей хранятся в localStorage, серверного аккаунта нет. Работай в текущем репозитории, сначала прочитай исходники и валидаторы. Не переписывай приложение на Next.js ради подключения БД. Сохрани гостевой режим, офлайн-практику, текущий дизайн и существующие идентификаторы контента.

Стек backend: Node.js + TypeScript + Hono, развёртывание API в Vercel Functions; доступ к PostgreSQL в Neon через Prisma ORM. Hono используется для маршрутов, middleware, авторизации запросов и обработки ошибок. Frontend остаётся React + Vite, без перехода на Next.js. Prisma, секреты и проверка соревновательных ответов работают только на сервере. Для старта не требуй платного Redis, платной рассылки или платного realtime-провайдера. Если выбранная возможность не входит в бесплатный тариф, явно покажи бесплатный резервный вариант.

Сначала реализуй БД, миграции, seed, авторизацию, перенос локальных данных и синхронизацию. Для соревнований подготовь схему, сервисы и минимальные тестируемые API; полноценное оформление экранов соревнований — отдельный этап. Не публикуй, не отправляй коммиты и не изменяй облачную БД без отдельной команды. Если облачные ключи отсутствуют, используй локальный PostgreSQL и .env.example; не объявляй облачную проверку выполненной.

Закрепление ошибки требует двух правильных повторений и паузы от последней ошибки не менее суток. Сохрани фактическое поведение и тесты, не меняй методику молча.

Не выдумывай отсутствующие исторические ответы: старые totals и дневные агрегаты — отдельная импортированная основа, а не поддельные Attempt-события. Не смешивай отметки «Знаю», проверенное слово, учебный XP, игровой уровень и CEFR.

Выбор голоса может не существовать на другом устройстве: общую скорость можно синхронизировать, voiceURI храни как настройку устройства с безопасным fallback. Микрофонные записи сейчас временные, не сохраняются и не отправляются: не вводи их автоматическую загрузку.

## 2. Схема и учебный контент

Используй осмысленные связанные модели, а не одну таблицу с JSON всего localStorage. JsonB допустим для версионированных снимков импорта, отдельных payload и редких настроек, но не вместо связей и индексов рабочих запросов.

Предложи и обоснуй модели следующих групп; конкретные названия можно улучшить:

1. Identity: User, профиль, настройки, Device, таблицы Account/Session выбранной библиотеки авторизации. Публичный профиль отдели от email и приватных учебных данных.
2. Catalog: Course, CourseLevel, Lesson, LessonStep, RuleTopic, Word, WordTranslation, NounForm, Verb, VerbForm, Exercise, ExerciseVersion, AnswerVariant. DE-контент и переводы RU/UK храни без искусственного заполнения отсутствующих переводов.
3. Learning: UserWordStatus, UserWordSkill, UserVerbFormProgress, UserNounProgress, UserSentenceProgress, UserLessonProgress, UserLessonStep, UserLessonNote, UserDailyPlan, UserDailyPlanWord, SavedPhrase, StudyDay, StudyEvent/Attempt, Mistake, MistakeRecovery, DailySummary. Не обязательно создавать по модели на каждое имя: избегай дублирования одной истины.
4. Rewards: AchievementDefinition, AchievementTier, UserAchievement, XpLedger. Одна награда развивается по ступеням, а не создаёт пачку одинаковых пользовательских карточек. Полученная ступень не исчезает после перерыва.
5. Sync: SyncEvent, ImportBatch, ImportMapping и при необходимости запись разрешённого конфликта. Импорт должен иметь source/schemaVersion/checksum/время/итог и возможность расследовать ошибку.
6. Competition: Season, QueueEntry, Match, MatchParticipant, MatchRound, RoundSubmission, MatchEvent, Rating, RatingHistory, LeaderboardEntry или запрос/агрегат вместо последней таблицы. Не добавляй таблицы без объяснения назначения.

Укажи обязательные поля, enum, nullable-семантику, FK, onDelete, уникальности, CHECK-ограничения и индексы. UUID допустимы как внутренние ID, но сохрани legacyKey/externalId: старые ID видео, слов, предложений и упражнений нельзя потерять. Версию вопроса зафиксируй в раунде: редактура контента не должна менять проверку уже сыгранной партии.

Импортируй реальный каталог из исходников идемпотентным seed: около 2000 слов, 71 глагол, 81 набор форм существительных, 1588 предложений, 228 видеоуроков и 8 мини-уроков. Проверь текущие числа, альтернативные ответы и генераторы. Не подменяй содержание демонстрационными записями. C1/C2 остаются без выдуманной программы. Для будущего предусмотрены дополнительные языки перевода и версии контента.

Время событий хранить в UTC/timestamptz; учебный день — DATE с явно заданной зоной Europe/Berlin для совместимости. Для сезона — единые серверные границы времени. Опиши переход на пользовательские зоны в будущем, не пересчитывая задним числом историю.

## 3. Авторизация, импорт и офлайн-синхронизация

- Выбери поддерживаемую библиотеку авторизации с Prisma/PostgreSQL. OAuth Google/GitHub — приемлемая основа без обязательной платной почты. Не реализуй хранение паролей самостоятельно. Объясни настройки провайдера и сессий.
- Гость продолжает учиться без аккаунта. При входе предложи перенос с предварительным просмотром, не стирай localStorage. Выход не должен показывать приватные данные другого аккаунта; локальный кэш должен иметь владельца.
- Импорт выполняется авторизованным API только в свой userId из сессии. client userId не является подтверждением личности. Валидация payload, лимиты размера/числа записей, версия формата, неизвестные legacy ID — отдельный отчёт.
- Повторный импорт одной копии и повторная отправка событий не удваивают XP, попытки, дни, ступени и дневные агрегаты. Уникальность deviceId + clientEventId, транзакции и проверяемые ревизии обязательны.
- Опиши стратегию по каждому типу конфликта: объединение освоенных ID, различие known/learning, заметки, настройки, ошибки и SRS. Нельзя бездумно суммировать counters с двух устройств или доверять клиентскому updatedAt. Устаревший импорт не перезаписывает более новые серверные изменения молча.
- Сохрани локальный кэш и офлайн-очередь; отправка пачками, подтверждение сервером, retry/backoff, восстановление после обрыва. Снимок старого прогресса — импортная основа; новые события не прибавляют её повторно. Запоздавшее офлайн-событие не откатывает актуальную SRS-ступень.
- Источник результата: LOCAL_IMPORT, OFFLINE, SERVER_VERIFIED. Импортированный прогресс сохраняет личную историю, но не выдаёт соревновательные баллы и рейтинг. Не называй старые агрегаты подтверждёнными сервером.
- Миграция постепенная, без обнуления существующих ключей. Подготовь экспорт/удаление данных аккаунта; удаление пользователя продумай отдельно от обезличенной истории матчей.

## 4. Рейтинг и соревнования

Учебный XP и соревновательный рейтинг — разные величины. Для личной истории импорт XP допустим с меткой происхождения; серверный рейтинг и соревновательные награды формируются только из проверенных результатов.

Режимы будущего MVP:

- SENTENCE_RACE: одинаковое задание для двух игроков; составить предложение из слов быстрее соперника. Проверка подготовленных допустимых вариантов — на сервере.
- WORD_CHOICE_RACE: немецкое слово и четыре перевода, один верный. Побеждает первый принятый сервером правильный ответ. Ошибка одного игрока не завершает раунд за всех. Одна финальная попытка на игрока в раунде; повтор запроса возвращает прежний результат, а не даёт новую попытку.

Подготовь расширение на комнаты с несколькими участниками, приглашения друзей, ranked/casual, уровни A1/A2/B1 и будущие дополнительные уровни.

Для матчей зафиксируй состояния очереди/матча/раунда, участников, выбранный контент и версию, startsAt/deadlineAt, serverReceivedAt, варианты конкретного раунда, результат, причину завершения/дисквалификации и историю рейтинга. Неправильный ответ не должен позволять спамить до угадывания.

Критические требования:

1. Сервер создаёт вопрос, непредсказуемый round token и окно приёма. До старта не отдавать вопрос для решения заранее; правильный вариант/ключ не отправлять клиенту до окончания раунда. Уже опубликованный учебный каталог не считать защищённым от ботов.
2. Правильность, очки и победителя определяет сервер. Клиентские correct, score и elapsedMs не принимаются как доказательство. clientSentAt — только диагностическое поле.
3. Одновременно пришедшие верные ответы разрешаются атомарно в PostgreSQL, с однозначной политикой ничьей. Unique(roundId,userId), защита от двойного winner/двойного начисления, транзакционные блокировки или CAS и повтор транзакции при конфликте. Запись результата и начисление согласованы.
4. Для MVP «кто первый» означает первым принят сервером; задержка сети влияет на результат. Не обещай абсолютную справедливость реакции. Опиши server timestamps, замер задержки для диагностики и возможное окно ничьей, не доверяя клиентской компенсации.
5. Reconnect, выход, истечение времени, отменённый матч и падение обработчика не оставляют матч навечно открытым. Дедлайны хранятся в БД; обработка истёкших состояний идемпотентна. setTimeout и память единственного процесса не являются источником истины.
6. Выбери объяснимый сезонный Elo для дуэлей: стартовый рейтинг, K, provisional-игры, ничья, минимальное число матчей до публичного рейтинга. Применение результата матча — ровно один раз. Для многопользовательского режима оставь явное расширение алгоритма, не применяй бинарную формулу вслепую.
7. Отдельные ranked/casual, фильтры по сезону/режиму/уровню, детерминированное место при равных баллах, история изменения рейтинга. Сезонный лидерборд не зависит от импортированного localStorage XP.
8. Авторизация участия, приватность комнат, серверная валидация каждого сообщения/запроса, rate limits и защита от replay/дубликатов. Ограничение ботов и сговора обозначь честно; абсолютную античит-защиту не обещай.

## 5. Realtime и бесплатный запуск

Выдели интерфейс транспорта, не привязывая доменную логику к одному WebSocket-соединению. Сначала обеспечь работоспособный HTTP API с ограниченным polling только в активной комнате; не опрашивай постоянно всю БД и не записывай heartbeat на каждый poll.

Проверь текущую документацию Vercel: native WebSocket на Functions доступен в beta, зависит от Fluid Compute и имеет ограниченное время соединения. При использовании реализуй reconnect/resume с lastEventId/sequence. Два игрока могут попасть на разные инстансы: in-memory Map не подходит для общей очереди, комнаты или победителя. PostgreSQL — долговременная истина; доставку событий между инстансами реши явно. Если используется polling как резерв, назови его ограничения для скоростных соревнований.

Не запускай отдельный бесконечный Socket.IO-сервер внутри обычного HTTP-обработчика. Не удерживай транзакцию PostgreSQL на время всей игры. На старте не делай обязательным Redis; предложи его как последующее улучшение при доказанной необходимости.

## 6. Сервер, Prisma и развёртывание

- Закрепи совместимые версии Prisma CLI/client/adapter; не смешивай разные major или стабильную версию с prerelease. Подготовь Prisma schema, prisma.config.ts, Prisma Client с Neon adapter и явным generated output.
- DATABASE_URL — pooled runtime URL; DATABASE_URL_UNPOOLED — direct URL для CLI/миграций. Настрой их по документации выбранной версии, не копируй синтаксис Prisma 6 в Prisma 7.
- Точка входа Hono API в api/, маршруты, middleware и общая серверная логика в server/, схема и миграции в prisma/. Свяжи маршруты /api/* с точкой входа по текущей документации Hono/Vercel. Не импортируй server/Prisma в React src. Сохрани фронтенд Vite, Node runtime для API. SPA fallback не должен перехватывать /api/*. Для локальной разработки настрой совместный запуск Vite и Hono с proxy /api, без необходимости публиковать приложение.
- Серверный экземпляр Prisma переиспользуется в тёплом процессе; соединения не открываются заново вручную на каждый запрос. Укажи ограничения pooling и транзакций.
- Секреты только в серверном окружении, никогда VITE_DATABASE_URL. Добавь .env* в .gitignore с исключением .env.example до создания секретов.
- Отдельные dev/preview/prod базы или ветки. Preview не запускает миграции/seed против production. Укажи явный порядок prisma generate → migrate deploy для выбранной среды → seed контента → проверка API → публикация приложения. Production migration не запускается в каждом запросе и не размножается на каждый preview build.
- Миграции SQL коммитятся. migrate dev — только разработка, migrate deploy — подготовленные миграции целевой среды. Не использовать db push/reset как production-процедуру. Seed идемпотентен и не меняет пользовательский прогресс.
- Добавь локальный PostgreSQL через Docker Compose как необязательный способ разработки. Предоставь .env.example без реальных секретов, скрипты генерации/миграций/seed и отдельную проверку серверного TypeScript.
- API авторизации/прогресса/соревнований не кэшируется публичным service worker или CDN. Проверь текущую PWA-конфигурацию; персональные ответы — private/no-store, офлайн-кэш привязан к аккаунту. Не сломай существующие статические офлайн-материалы.

## 7. Результат и проверки

Сначала кратко обоснуй схему и таблицу миграции всех localStorage-ключей, затем создай рабочие файлы. Дай ER-диаграмму Mermaid и инструкцию DATABASE-SETUP.md понятным языком.

Обязательные проверки на реальном PostgreSQL: seed дважды без дублей; импорт дважды без удвоения; импорт двух устройств с пересечением; конфликт статуса/заметки; запоздавшее событие и SRS; сохранение старых ID и дневного журнала; недоступность чужого прогресса; импорт XP не влияет на ranked; сервер отклоняет подмену score/correct/userId; две конкурентные транзакции не выдают две победы; двойная отправка ответа/результата не начисляет рейтинг дважды; дедлайн и reconnect; альтернативный правильный порядок слов; граница суток/DST и сезона. Моки не заменяют проверку гонок транзакций в PostgreSQL.

Запусти прежние тесты и сборку фронтенда, новые серверные проверки и миграции на тестовой БД. В конце перечисли выполненное, проверенное и то, для чего ещё нужны OAuth-настройки/секреты/облачное подключение. Без отдельного разрешения не создавай облачные ресурсы и не публикуй изменения.
